# 概念篇：认识 Dockerfile

Dockerfile 记录应用的镜像怎样构建、容器怎样启动。先理解镜像和容器的关系，再按用途查找指令。

## 镜像和容器

- **Docker** 提供构建、分发镜像和运行容器的工具。
- **镜像（Image）** 包含应用、依赖和启动配置，是创建容器时使用的只读模板。
- **容器（Container）** 是从镜像创建的实例。运行时，应用以隔离进程的方式执行。一个镜像可以启动多个容器。

团队可以把同一镜像用于测试和部署，减少应用版本与依赖环境的差异。

## Dockerfile 是什么？

Dockerfile 是一个包含指令和参数的文本文件。构建时，Docker 根据它选择基础镜像、安装依赖和复制文件，同时记录容器启动时使用的默认配置。

**Dockerfile 的基本规则：**

- 指令**不区分大小写**，但**推荐使用大写**，更清晰。
- 用单独的 `#` 行写注释。文件顶部的 `# syntax=...` 用于指定解析器。
- `FROM` 开始一个构建阶段。它之前可以声明用于选择基础镜像的 `ARG`。
- `RUN`、`COPY` 和 `ADD` 通常会产生文件系统层。`LABEL`、`CMD` 和 `ENV` 写入镜像配置。

一个典型的 Dockerfile 结构可能包含：

1.  **基础镜像信息：** 使用 `FROM` 指令指定依赖的基础镜像。
2.  **(可选) 维护者信息：** 使用 `LABEL` 指令添加元数据。
3.  **镜像构建指令：** 使用 `RUN`, `COPY`, `ADD` 等指令来安装软件、复制文件等。
4.  **容器启动指令：** 使用 `CMD`, `ENTRYPOINT` 等指令指定容器启动时执行的命令。

## Dockerfile 常用指令详解

按实际顺序阅读时，可以先看 `FROM`、`RUN` 和 `COPY`，再看 `CMD` 和 `ENTRYPOINT`。以下代码块分别演示单条指令的用途。

### FROM

`FROM` 指定本阶段基于哪个镜像构建。多阶段构建有多个 `FROM`，可用 `AS` 为阶段命名，便于后续用 `COPY --from` 引用产物。

**格式：**

```dockerfile
FROM [--platform=<platform>] <image> [AS <name>]
FROM [--platform=<platform>] <image>[:<tag>] [AS <name>]
FROM [--platform=<platform>] <image>[@<digest>] [AS <name>]
```

**示例：**

```dockerfile
# 使用官方的 Ubuntu 最新版作为基础镜像
FROM ubuntu:latest

# 使用特定版本的 Alpine Linux 作为基础镜像，并给这个阶段命名为 builder
FROM alpine:3.18 AS builder
```

> **中小企业提示：** 选择基础镜像很重要！尽量选择官方、受信任且体积小的镜像（如 `alpine`、`debian-slim`），可以显著减小最终镜像的大小，加快下载和部署速度，并减少安全风险。

### LABEL

**用途：** 为镜像添加**元数据 (Metadata)**，如版本号、描述、作者等。这些信息不会影响镜像功能，但有助于管理和识别镜像。

**格式：**

```dockerfile
LABEL <key>=<value> <key>=<value> <key>=<value> ...
```

**示例：**

```dockerfile
LABEL version="1.0" description="我的第一个 Web 应用镜像" maintainer="Your Name <you@example.com>"
```

### RUN

**用途：** 在**构建镜像过程**中执行指定的命令。通常用于安装软件包、创建目录、编译代码等。

**格式：**

```dockerfile
# Shell 格式 (简单命令推荐)
RUN <command>

# Exec 格式 (官方推荐，尤其适合包含空格或特殊字符的命令)
RUN ["executable", "param1", "param2"]
```

**示例：**

```dockerfile
# 更新软件包列表并安装 Nginx (Shell 格式)
RUN apt-get update && apt-get install -y nginx

# 创建一个目录 (Exec 格式)
RUN ["mkdir", "/app"]
```

> 把关联的操作放在同一条 `RUN` 里，例如更新软件包索引、安装软件包和清理索引。用 `&&` 连接可在某一步失败时停止执行，并让临时文件在这一层写入镜像前被清理。
>
> ```dockerfile
> RUN apt-get update && \
>     apt-get install -y --no-install-recommends software-properties-common && \
>     apt-get clean && \
>     rm -rf /var/lib/apt/lists/*
> ```

### CMD

`CMD` 提供容器启动时的默认命令。每个构建阶段只需写一条 `CMD`，重复定义时以该阶段最后一条为准。配合 exec 形式的 `ENTRYPOINT` 时，`CMD` 可只提供默认参数。

**格式：**

```dockerfile
# Shell 格式
CMD command param1 param2

# Exec 格式 (官方推荐)
CMD ["executable","param1","param2"]

# 作为 ENTRYPOINT 的默认参数 (后面会讲)
CMD ["param1","param2"]
```

**示例：**

```dockerfile
# 容器启动时运行 python server.py (Exec 格式)
CMD ["python", "server.py"]

# 容器启动时执行 /bin/bash (Shell 格式)
CMD /bin/bash
```

> **注意：** 如果在 `docker run` 命令后面指定了其他命令，`CMD` 指定的命令会被覆盖。

### ENTRYPOINT

`ENTRYPOINT` 指定容器启动的入口程序。需要让调用者保留同一个程序、只更换参数时，使用 exec 形式的 `ENTRYPOINT`，并用 `CMD` 提供默认参数。临时更换程序可用 `docker run --entrypoint`。

**格式：**

```dockerfile
# Shell 格式
ENTRYPOINT command param1 param2

# Exec 格式 (官方推荐)
ENTRYPOINT ["executable", "param1", "param2"]
```

**`ENTRYPOINT` 和 `CMD` 的配合使用：**

- 如果只用 `ENTRYPOINT` (Exec 格式)，`docker run` 命令行后面的参数会**追加**到 `ENTRYPOINT` 命令之后。
- 如果同时使用 `ENTRYPOINT` (Exec 格式) 和 `CMD` (Exec 格式，且 `CMD` 提供的是参数列表)，`CMD` 的内容会作为 `ENTRYPOINT` 的**默认参数**。如果在 `docker run` 时提供了参数，则会**覆盖** `CMD` 提供的默认参数。

**示例：**

```dockerfile
# Dockerfile
ENTRYPOINT ["ls"]
CMD ["-a"]

# 运行 `docker run <image>` 时，实际执行 `ls -a`
# 运行 `docker run <image> -l` 时，实际执行 `ls -l` (-l 覆盖了 CMD 的 -a)
```

> **何时使用？** 如果你想让容器表现得像一个固定的可执行文件，并且允许用户传递参数给这个文件，那么 `ENTRYPOINT` (Exec 格式) + `CMD` (参数格式) 是常用模式。如果只是想提供一个默认的启动命令，且允许用户完全替换它，那么单独使用 `CMD` 更简单。

### EXPOSE

`EXPOSE` 记录应用预计在容器内监听的端口和协议。由应用配置实际监听端口，由 `docker run` 配置宿主机如何访问该端口。

**格式：**

```dockerfile
EXPOSE <port> [<port>/<protocol>...]
```

**示例：**

```dockerfile
# 声明容器将监听 80 端口 (默认 TCP)
EXPOSE 80

# 声明容器将监听 80/tcp 和 443/tcp 端口
EXPOSE 80/tcp 443/tcp
```

> `docker run -p 8080:80 <image>` 把宿主机的 8080 端口映射到容器的 80 端口。使用 `-P` 时，Docker 会为 `EXPOSE` 声明的端口分配宿主机端口，可用 `docker port` 查看。

### VOLUME

`VOLUME` 声明可以挂载数据的容器路径。运行容器时可在该路径挂载 Docker 管理的命名卷或指定的宿主机目录。

**格式：**

```dockerfile
VOLUME ["<path1>", "<path2>"...]
VOLUME <path>
```

**示例：**

```dockerfile
# 声明 /data 目录用于存储持久化数据
VOLUME ["/data"]

# 声明 /app/config 和 /app/logs 用于挂载配置和日志
VOLUME /app/config /app/logs
```

> 容器运行时向该路径写入的数据保存在挂载的卷里。需要让新容器接着用这份数据时，用 `docker run -v` 指定命名卷或宿主机目录。Docker 自动创建的匿名卷在使用 `--rm` 删除容器时也会被移除。

### COPY

`COPY` 默认从构建上下文复制文件。上下文由 `docker build` 最后的参数指定。即使通过 `-f` 改变 Dockerfile 的位置，源路径也相对于上下文解析。使用 `COPY --from` 时，可以从另一个构建阶段或镜像复制文件。

**格式：**

```dockerfile
COPY [--chown=<user>:<group>] [--chmod=<perms>] <src>... <dest>
# 路径含空格时使用 JSON 格式
COPY [--chown=<user>:<group>] [--chmod=<perms>] ["<src>", "<dest>"]
```

**示例：**

```dockerfile
# 将当前目录下的 app.py 文件复制到镜像的 /app/ 目录下
COPY app.py /app/

# 将当前目录下的 config 目录复制到镜像的 /etc/myapp/config/ 目录下
COPY config/ /etc/myapp/config/
```

> **最佳实践：**
>
> - 只复制你需要的文件和目录，避免将不必要的文件（如 `.git` 目录、临时文件）复制进镜像。可以使用 `.dockerignore` 文件来排除它们。
> - 复制上下文中的普通文件时，优先用 `COPY`。需要解包本地归档时，可用 `ADD`。

### ADD

**用途：** 与 `COPY` 类似，但功能**更强大**：

1.  可以复制本地文件/目录到镜像。
2.  如果源 `<src>` 是一个 **URL**，它会尝试下载文件并复制到 `<dest>`。
3.  如果源 `<src>` 是一个本地的 **tar 压缩包** (如 `.tar.gz`, `.tar.bz2`, `.tar.xz`)，它会自动解压到 `<dest>`。

**格式：** 与 `COPY` 相同。

**示例：**

```dockerfile
# 下载一个文件并放到 /tmp/
ADD https://example.com/file.zip /tmp/

# 复制本地的 myapp.tar.gz 并自动解压到 /usr/src/
ADD myapp.tar.gz /usr/src/
```

> **注意：** 由于 `ADD` 的行为（特别是自动解压和下载）有时不够透明和可控，**官方更推荐**：
>
> - 复制本地文件/目录：使用 `COPY`。
> - 下载文件：使用 `RUN wget` 或 `RUN curl`，这样更清晰，且可以在同一步骤中进行解压、清理等操作。

### ENV

`ENV` 设置环境变量的默认值。后续 `RUN` 可读取它，启动的容器也会继承它。运行时可用 `docker run -e` 覆盖这个值。

**格式：**

```dockerfile
ENV <key>=<value> ...
# 旧格式
ENV <key> <value>
```

**示例：**

```dockerfile
# 设置应用版本和工作目录
ENV APP_VERSION="1.0" WORK_DIR="/app"

# 在后续指令中使用环境变量
WORKDIR $WORK_DIR
RUN echo "Building version $APP_VERSION" > version.txt
```

> **注意：** 使用 `ENV` 设置的环境变量会**持久存在于镜像和容器**中。如果只是想在构建过程中临时使用变量，应该考虑使用 `ARG`。

### ARG

**用途：** 定义**构建时变量**。这些变量只在 `docker build` 过程中有效，容器运行时不可用（除非用 `ENV` 重新定义）。可以通过 `docker build --build-arg <name>=<value>` 来传递值。

**格式：**

```dockerfile
ARG <name>[=<default value>]
```

**示例：**

```dockerfile
# 定义构建时用户名
ARG APP_USER=appuser
RUN useradd "$APP_USER"

# 如果希望构建参数在容器中也可用，可以结合 ENV
ARG APP_PORT=8080
ENV PORT=$APP_PORT
EXPOSE $PORT
```

**构建时传递参数：**

```shell
docker build --build-arg APP_USER=webapp --build-arg APP_PORT=9090 -t myimage .
```

`ARG` 适合传递版本号、端口等构建配置。构建参数可能出现在镜像历史或构建证明中，密码和令牌应使用 [BuildKit secret mount](https://docs.docker.com/build/building/secrets/) 临时注入。

### WORKDIR

`WORKDIR` 设置后续 `RUN`、`CMD` 和 `ENTRYPOINT` 的工作目录。如果目录不存在，Docker 会创建它。`COPY` 和 `ADD` 的相对目标路径也从此目录计算，本地源文件仍按构建上下文查找。

**格式：**

```dockerfile
WORKDIR /path/to/workdir
```

**示例：**

```dockerfile
WORKDIR /app

# 下面的 COPY 和 RUN 都在 /app 目录下执行
COPY . .
RUN pip install -r requirements.txt

WORKDIR /data
# 现在工作目录切换到了 /data

# 可以使用相对路径
WORKDIR /app
WORKDIR sub-dir
# 输出 /app/sub-dir
RUN pwd
```

> **最佳实践：** 推荐使用绝对路径，并尽量在 Dockerfile 开头就设置好主要的工作目录，避免在根目录 (`/`) 下执行过多操作。
