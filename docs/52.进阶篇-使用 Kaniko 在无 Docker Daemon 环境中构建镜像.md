# 进阶篇：镜像生命周期管理与维护

本章处理两项日常工作。清理旧镜像时，先核对部署和回滚需要的版本，再试运行保留策略与垃圾回收。更新基础镜像时，先查清下游依赖，再按顺序重建并验证产物。

## 一、回顾与标准化：管理的基础

给镜像和标签保留能追查来源的信息，方便核对保留策略、依赖和回滚版本。[镜像分层与管理规范](21.设计篇-Dockerfile%20设计原则与镜像管理规范.md)

- **清晰的命名规范:** `<仓库名>/<项目名>/<镜像名>:<标签>`，有助于分类和查找。
- **一致的版本标签策略:** 使用语义化版本、日期戳、Git Commit ID 等，方便追踪版本和回滚。
- **合理的仓库/项目结构:** 在 Harbor 等 Registry 中按逻辑（如 `common`, `dev`, `test`, `prod`）或团队组织项目，便于权限控制和管理。
- **记录镜像元数据**。用 Dockerfile 的 `LABEL` 记录维护者、代码仓库、基础镜像来源和构建时间。通过镜像标签（Tag）选版本，通过这些元数据了解如何构建该版本。

## 二、镜像清理策略：节省空间与降低风险

先确定哪些旧镜像仍用于部署或回滚，再清理过期、未使用或已被替代的漏洞镜像。

### 1. 利用 Harbor 的保留策略 (推荐)

在 Harbor 中按项目设置保留策略。规则决定保留哪些制品，试运行用于核对预计移除的对象。

- **配置入口:** 进入 Harbor 项目 -> 策略 -> 保留策略 -> 添加规则。
- **常用规则:**
  - **按数量保留:** 保留最近推送的 N 个镜像 (`retain the most recently pushed N artifacts`)。
  - **按时间保留:** 保留最近 N 天/周/月内推送过的镜像 (`retain the artifacts pushed within the last N days`)。
  - **保留指定标签：** 为 `latest` 或 `stable-*` 单独添加 `retain always` 规则。规则按制品摘要生效，同一摘要的其他标签也会保留。[Harbor 标签保留规则](https://goharbor.io/docs/2.13.0/working-with-projects/working-with-images/create-tag-retention-rules/)
  - **处理无 Tag 镜像:** 决定是否保留没有 Tag 的镜像 (通常不保留)。
- **执行计划:** 可以设置定时自动执行（如每天、每周），也可以手动执行。
- **试运行 (Dry Run):** 在实际删除前，先进行试运行，查看哪些镜像会被清理。

按项目用途选择保留周期。

- 为 `dev` 和 `test` 环境设置较短的保留策略（如保留最近 10-30 个或 7-30 天）。
- 为 `prod` 环境设置更长的保留策略，或根据合规要求确定。
- 为 `common` (基础镜像) 项目通常保留主要的稳定版本和最新的小版本, 并根据需要保留一些历史版本。

### 2. Harbor 垃圾回收 (GC)

保留策略移除到期制品后，仍需运行**垃圾回收 (Garbage Collection, GC)** 才能释放未被镜像清单引用的镜像层占用的空间。

- **配置入口:** 系统管理 -> 清理服务 (Garbage Collection)。
- **执行计划:** 设置定时自动执行（如每周一次，建议在低峰期）。
- 先执行 **Dry Run** 并核对预计回收对象。启用清理无标签制品前，核对仍被部署配置按摘要引用的镜像。[Harbor 垃圾回收](https://goharbor.io/docs/2.13.0/administration/garbage-collection/)

### 3. 本地 Docker 环境清理

开发或构建节点上的镜像和缓存单独清理。先用 `docker system df -v` 查看占用，再根据要删除的对象选一条清理命令。

```bash
# 查看镜像、容器、卷和构建缓存占用
docker system df -v

# 删除无标签且未被容器使用的镜像
docker image prune

# 删除所有未被容器使用的镜像
docker image prune -a

# 删除未使用的构建缓存
docker builder prune

```

执行 `prune -a` 前核对是否有仅保留在本机、用于回滚的镜像。`docker system prune --volumes` 还会清理未使用的匿名卷，可能删除已拆除容器留下的数据。[Docker 清理范围](https://docs.docker.com/reference/cli/docker/system/prune/)

## 三、基础镜像与依赖更新流程

更新基础镜像前，先记录原标签和受影响的下游应用。使用以下流程产出和验证新的基础镜像。

1. **监控上游更新:** 关注您使用的基础镜像（如 `debian`, `python`, `node`）和关键依赖库的安全公告和新版本发布。可以利用自动化工具或订阅服务。
2. **定期更新基础镜像:**
   - 为您的标准化基础镜像（如 `common/os/debian`)建立定期的更新计划（例如每月或每季度）。
   - 更新 Dockerfile 中的 `FROM` 指令到最新的稳定小版本或验证过的大版本。
   - 重新构建基础镜像，并进行充分的测试（例如，用它构建几个代表性的下游应用镜像并测试应用功能）。
   - 测试通过后，推送新的基础镜像 Tag 到 Harbor。
3. **按依赖顺序更新下游**。用下一节的方法查清依赖和构建顺序。
4. **定期更新应用依赖:**
   - 鼓励开发团队定期更新 `requirements.txt`, `package-lock.json`, `go.mod` 等文件中的依赖版本。
   - 运行 `npm audit`, `pip-audit`, `trivy fs .` 等工具检查应用依赖漏洞。
   - 更新依赖后，重新构建并测试应用镜像。

## 四、管理依赖关系与批量更新

以 `common/os/debian` 更新为例，先确认哪些工具镜像和应用镜像引用了旧版，再决定各项目的重建方式。

1. **基于命名/标签约定 (简单但不完全可靠):** 如果您的镜像标签包含了基础镜像信息（如 `python:3.11-debian11`），可以通过脚本扫描 Harbor API，根据标签模式查找下游。缺点是不够精确，且依赖严格遵守约定。
2. **基于镜像 `LABEL`：** 在仓库侧查询基础镜像摘要，将同一份带摘要的引用用于 `FROM` 和镜像标签。以下以 Nginx 为例。
   ```Dockerfile
   ARG BASE_IMAGE=public.ecr.aws/docker/library/nginx:stable-alpine
   FROM ${BASE_IMAGE}
   ARG BASE_IMAGE
   LABEL com.example.build.base="${BASE_IMAGE}"
   ```
   在保存 `Dockerfile` 的目录执行以下命令，需 Bash 和 `shasum`。
   ```bash
   set -o pipefail
   base_image=public.ecr.aws/docker/library/nginx:stable-alpine
   base_hash=$(docker buildx imagetools inspect --raw "$base_image" | shasum -a 256 | cut -d ' ' -f 1) &&
     docker buildx build --load --build-arg "BASE_IMAGE=${base_image}@sha256:${base_hash}" -t base-label-demo . &&
     docker image inspect base-label-demo --format '{{index .Config.Labels "com.example.build.base"}}'
   ```
   多架构标签解析得到镜像索引摘要。回读的标签可用于追踪构建时固定的源引用。[Buildx 摘要查询](https://docs.docker.com/reference/cli/docker/buildx/imagetools/inspect/)
3. **基于 Dockerfile 分析：** 检查每个构建阶段的 `FROM` 和 `COPY --from`。遇到变量时，结合 Dockerfile 中的 `ARG` 默认值和实际构建参数解析。

**批量更新触发机制:**

一旦基础镜像更新并推送了新的 Tag (例如 `common/os/debian:bullseye-slim-20240805` 和 `common/os/debian:bullseye-slim`)，可以通过以下方式触发下游更新：

- **手动触发:** 通知相关团队或运维人员手动更新其应用的 Dockerfile 或 CI/CD 配置中的 `FROM` 指令，并触发重新构建。
- **CI/CD 自动化:**
  - **定时检查:** CI/CD 系统（如 Jenkins）可以定时检查基础镜像是否有新版本，或者扫描下游镜像的 Label 发现使用了旧基础镜像，然后自动触发下游 Pipeline。
  - **Webhook/事件驱动:** 更高级的方式是，当基础镜像构建成功并推送到 Harbor 后，通过 Harbor Webhook 或其他事件机制，自动触发依赖该镜像的下游 Pipeline。这需要更复杂的 CI/CD 配置。

### 查看依赖并安排构建

在仓库根目录使用 Bash 4 或更高版本运行镜像管理器。先查标签，再确认直接和间接依赖。[镜像管理脚本](../dockerfiles/image_manager.sh)

```bash
bash dockerfiles/image_manager.sh list
bash dockerfiles/image_manager.sh deps common/tools/openjdk
bash dockerfiles/image_manager.sh tree common/tools/openjdk
```

`list` 显示构建脚本声明的标签，`deps` 显示所选镜像引用的基础镜像、构建产物和直接下游，`tree` 继续展开间接下游。比如 `common/tools/openjdk` 更新后，可以顺着运行时镜像找到 Spring Boot 模板。

脚本读取 `Dockerfile` 和同目录变体的 `FROM`，使用全局 `ARG` 默认值和仓库构建脚本中的字面参数，按完整仓库地址和标签匹配。按摘要固定的基础镜像或由流水线计算的参数应单独核对。

先推送作为起点的镜像，再按依赖顺序构建其下游。此命令会调用公共镜像目录的 `build.sh`，并推送镜像到脚本设置的仓库。

```bash
bash dockerfiles/image_manager.sh build common/tools/openjdk
```

首次失败时，命令返回失败并停止后续构建。重试前核对已经推送的标签。命令会列出并跳过缺少 `build.sh` 的模板，Spring Boot 等应用仍在自己的代码仓库构建。

## 五、安全集成到维护流程

- **定期重新扫描:** 即使镜像没有重新构建，漏洞数据库是不断更新的。配置 Harbor 定期重新扫描存量镜像，或通过 CI/CD 定时任务运行 `trivy image`。
- **建立处理流程:** 对于扫描发现的新漏洞（特别是高危和严重），建立明确的处理流程：评估 -> 制定修复计划 (更新基础镜像/依赖) -> 测试 -> 重新构建部署。
- **基线管理:** 定义组织可接受的漏洞基线（例如，不允许存在 Critical/High 漏洞，或只允许存在 `wont-fix` 的漏洞），并在 CI/CD 中强制执行。

## 六、维护后的核对

- 清理后确认当前部署和可回滚版本仍可拉取，对照垃圾回收结果核对释放的空间。
- 更新后检查 Harbor 中的基础镜像标签、下游构建结果和代表性应用测试。
- 对照流水线和定期扫描结果，确认仍需处理的漏洞已进入修复流程。[扫描与修复 Docker 镜像漏洞](50.进阶篇-扫描与修复%20Docker%20镜像漏洞.md)
