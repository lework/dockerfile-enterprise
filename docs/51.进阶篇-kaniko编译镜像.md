# 进阶篇：使用 Kaniko 在无 Docker Daemon 环境中构建镜像

本章用于维护已有的 Kaniko v1.9.0 流水线。执行器在容器内读取 Dockerfile、构建镜像并推送到指定仓库，可在非特权 Kubernetes Pod 中运行，无需访问宿主机 Docker Socket。Google 上游仓库于 2025 年 6 月 3 日归档。[Kaniko 上游仓库](https://github.com/GoogleContainerTools/kaniko)

**执行器镜像**

- `gcr.io/kaniko-project/executor:latest` 是标准执行器的通用标签。自动化流程使用明确版本，本章固定为 `v1.9.0`。
- `gcr.io/kaniko-project/executor:debug` 包含 BusyBox shell，可用于调试。

## Kaniko 是如何工作的？

Kaniko 的核心原理是在其自身的容器环境中，一步步执行 Dockerfile 中的指令：

1.  **提取基础镜像文件系统:** Kaniko 从指定的 Registry 拉取 Dockerfile 中 `FROM` 指令指定的基础镜像。
2.  **逐条执行指令:** Kaniko 在执行器容器内执行 `RUN`、`COPY`、`ADD` 等指令。
3.  **生成层快照:** Kaniko 对文件系统变化取快照，并将变化打包成镜像层。
4.  **更新镜像元数据:** 根据 Dockerfile 指令（如 `ENV`, `EXPOSE`, `CMD`）更新镜像的配置信息。
5.  **推送镜像层和配置:** 将新生成的层和最终的镜像配置文件推送到目标 Registry。

## 如何运行 Kaniko？

本地用 Docker 启动执行器，便于核对 Dockerfile 和仓库配置。已有流水线在 Kubernetes 中运行时，使用下面的 Job 示例。两个示例都需要可拉取执行器镜像、访问基础镜像并推送到目标和缓存仓库。

### 关键参数说明：

- `--dockerfile <path>` 或 `-f <path>`: 指定 Dockerfile 的路径（相对于构建上下文）。默认为 `./Dockerfile`。
- `--context <path>` 或 `-c <path>`: 指定构建上下文的路径。这是 Kaniko 读取 Dockerfile 和执行 `COPY`/`ADD` 指令的根目录。支持：
  - 本地目录 (挂载到容器内，如 `/workspace`)。
  - 远程 Git 仓库：`git://<repo_url>[#<ref>][#<commit>]`。
  - 远程归档示例：`gs://...`、`s3://...`。其他来源见 [v1.9.0 的上下文说明](https://github.com/GoogleContainerTools/kaniko/blob/v1.9.0/README.md#kaniko-build-contexts)。
  - 默认为 `/workspace`。
- `--destination <image_name>:<tag>` 或 `-d <image_name>:<tag>`: **必需参数**，指定构建完成后要推送到的目标镜像仓库地址和标签。可以指定多个 `-d` 来推送多个标签。
- `--cache=[true|false]`: 是否启用 Kaniko 的层缓存。默认为 `false`。启用后，Kaniko 会尝试复用之前构建过的层。
- `--cache-repo <image_name>` 指定层缓存的存取位置。例如在 CI/CD 中使用 `--cache=true --cache-repo your-registry/kaniko-cache`。
- `--build-arg <key>=<value>`: 传递构建参数给 Dockerfile。
- `--no-push`: 只构建镜像，不推送到目标仓库（用于测试或本地构建）。
- `--verbosity <level>`: 设置日志级别 (如 `info`, `debug`, `trace`)。

### 场景一：在本地使用 Docker 运行 Kaniko (用于测试)

本地通过 Docker 启动执行器。先将有目标仓库推送权限、基础镜像拉取权限的专用 Docker 认证配置准备为 `KANIKO_DOCKER_CONFIG` 指向的文件。配置须包含执行器可用的 `auths`，仅能在宿主机运行的凭证助手无法在执行器中使用。将域名和 IP 替换为自己的实验环境。

```bash
# 1. 克隆示例代码仓库
git clone https://github.com/lework/ci-demo-go.git

git_commit_id=$(git -C ci-demo-go rev-parse --short HEAD)

docker run --rm \
  --mount "type=bind,source=$PWD/ci-demo-go,target=/workspace" \
  --mount "type=bind,source=${KANIKO_DOCKER_CONFIG:?请指定专用 Docker 认证配置},target=/kaniko/.docker/config.json,readonly" \
  --add-host harbor.leops.local:192.168.77.140 \
  --add-host goproxy.leops.local:192.168.77.140 \
  gcr.io/kaniko-project/executor:v1.9.0 \
  --cache=true \
  --cache-repo=harbor.leops.local/dev/kaniko-go-cache \
  --context=dir:///workspace \
  --dockerfile=Dockerfile-kaniko \
  --destination="harbor.leops.local/dev/ci-demo-go:master-$git_commit_id" \
  --build-arg=APP=ci-demo-go \
  --build-arg=APP_ENV=dev \
  --build-arg=GIT_BRANCH=master \
  --build-arg="GIT_COMMIT_ID=$git_commit_id"
```

在构建日志中核对推送结果，再到 Harbor 的 `dev/ci-demo-go` 仓库确认标签由 `master-` 和本次 Git 短提交号组成。

### 场景二：在 Kubernetes 中使用 Kaniko (主要场景)

Jenkins、GitLab CI 或 Tekton 可以用一个 Kubernetes Job 运行示例。执行前选定实验命名空间，并确认当前 `kubectl` 上下文指向该环境。

1.  **准备 Docker 配置文件 Secret:** 将你的 `config.json` 文件（包含推送到目标仓库的认证信息）创建为一个 Kubernetes Secret。

    ```bash
    kubectl create secret generic regcred \
      --from-file=".dockerconfigjson=${KANIKO_DOCKER_CONFIG:?请指定专用 Docker 认证配置}" \
      --type=kubernetes.io/dockerconfigjson
    ```

    Secret 与 Job 位于同一命名空间。使用 `kubernetes.io/dockerconfigjson` 类型，专用认证配置覆盖目标、私有基础镜像和缓存仓库所需的权限。

2.  **准备构建上下文:**

    - **方法一（Git 仓库）**。使用 `git://<repo_url>`。私有仓库可用 Kubernetes Secret 注入 `GIT_TOKEN`，将访问令牌留在 Secret 中。[Kaniko 私有仓库认证](https://github.com/GoogleContainerTools/kaniko/blob/v1.9.0/README.md#using-private-git-repository)
    - **方法二 (Volume):** 通过 CI/CD 工具先将代码 checkout 到一个持久卷声明 (PVC) 或 `emptyDir` Volume 中，然后将此 Volume 挂载给 Kaniko Pod 的构建上下文路径 (默认为 `/workspace`)。
    - **方法三 (Init Container):** 使用 Init Container (例如 `alpine/git` 镜像) 在 Kaniko Pod 启动前将代码克隆到一个共享的 Volume (如 `emptyDir`) 中。

3.  **创建 Kubernetes Job 或 Pod:**

    运行 Kaniko 构建任务通常使用 Kubernetes Job，因为它代表一个批处理任务，完成后即结束。

    **示例 Kubernetes Job (`kaniko-job.yaml`):**

    ```yaml
    apiVersion: batch/v1
    kind: Job
    metadata:
      name: kaniko-image-build
    spec:
      backoffLimit: 0 # Job 失败时不进行重试
      template:
        spec:
          containers:
            - name: kaniko
              image: gcr.io/kaniko-project/executor:v1.9.0
              args:
                - '--context=git://github.com/lework/ci-demo-go.git#refs/heads/master' # 构建上下文：从 Git 仓库拉取
                - '--dockerfile=Dockerfile-kaniko' # Dockerfile 在仓库中的路径
                - '--destination=harbor.leops.local/dev/ci-demo-go:kaniko-demo' # 目标镜像仓库和标签
                - '--cache=true' # 启用 Kaniko 层缓存
                - '--cache-repo=harbor.leops.local/dev/kaniko-go-cache' # 指定用于存储缓存的远端镜像仓库 (推荐)
                - '--verbosity=info' # 日志级别
                - '--build-arg=APP=ci-demo-go' # 构建参数
                - '--build-arg=APP_ENV=dev'
                - '--build-arg=GIT_BRANCH=master'
              resources:
                requests:
                  memory: "1Gi"
                  cpu: "500m"
                limits:
                  memory: "4Gi"
                  cpu: "2"
              volumeMounts:
                # 挂载包含 Docker config.json 的 Secret 到 Kaniko 期望的路径
                - name: docker-config
                  mountPath: /kaniko/.docker/
                  readOnly: true # 建议以只读方式挂载凭证
          restartPolicy: Never # Job 完成或失败后不重启 Pod
          volumes:
            # 定义 Volume 来引用之前创建的 regcred Secret
            - name: docker-config
              secret:
                secretName: regcred # Secret 的名称
                items:
                  # 将 Secret 中的 .dockerconfigjson 数据项挂载为名为 config.json 的文件
                  - key: .dockerconfigjson
                    path: config.json
          hostAliases:
            # 添加额外的主机名解析 (可选)
            - ip: 192.168.77.140
              hostnames:
                - harbor.leops.local
                - goproxy.leops.local
    ```

    换成可访问的目标仓库、缓存仓库和域名映射后，在已经创建 `regcred` 的实验命名空间运行以下命令。[Kubernetes Job 字段](https://kubernetes.io/docs/concepts/workloads/controllers/job/)

    ```bash
    kubectl apply --dry-run=server --validate=strict -f kaniko-job.yaml
    kubectl apply -f kaniko-job.yaml
    kubectl wait --for=condition=complete --timeout=10m job/kaniko-image-build
    kubectl logs job/kaniko-image-build
    ```

    在日志中核对 `master` 分支、`Dockerfile-kaniko` 和 `dev/kaniko-go-cache`。Job 完成后，在 Harbor 的 `dev/ci-demo-go` 仓库确认 `kaniko-demo` 标签已生成。

## 与 Dockerfile 的兼容性

复用现有 Dockerfile 前，先核对下面几处常见差异。

- **`COPY --link`**。BuildKit 将复制内容写到独立的层，以便在基础层变化后复用。此处的 Kaniko 版本用普通 `COPY`。[Dockerfile COPY 参考](https://docs.docker.com/reference/dockerfile/#copy---link)

  - 例如，将 `COPY --from=builder --link /app /app` 修改为 `COPY --from=builder /app /app`。

- **部分 `RUN` 指令的行为差异**:

  - **特权操作**: 依赖于 Docker Daemon 特权的操作（例如，挂载某些类型的文件系统、修改内核参数等）在 Kaniko 中无法执行，因为 Kaniko 在非特权容器中运行。
  - **网络相关**: 某些依赖于 Docker Daemon 网络配置的 `RUN` 指令行为可能有所不同。

- **多阶段构建中的缓存**: 虽然 Kaniko 支持多阶段构建和层缓存 (`--cache=true`)，但其缓存命中逻辑和效率可能与 Docker BuildKit 的缓存有所不同。

- **BuildKit 特有语法**。已有 Dockerfile 使用 `RUN --mount=type=cache` 或 `RUN --mount=type=secret` 时，先核对执行器支持的语法。

维护现有流水线时，以所用执行器版本的文档为准。调整 Dockerfile 后，先在实验仓库构建一次并检查镜像产物，再接入原流水线。
